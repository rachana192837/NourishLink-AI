1 · What this project tests

Three ways to turn donated food into delivery plans: A — pure rule engine (FEFO: nearest-expiry first, urgent requests first); B — the same engine, but the AI demand forecast re-orders requests so shortage products are served before they run out; C — an AI agent pair (Inventory Analyst + Distribution Planner) writes the plan through audited tools that call the same rule engine underneath. All three run on exactly the same scenario {% if scenario.n_requests %} (the {{ scenario.n_requests }} earliest pending requests of {{ scenario.open_backlog }} open ones, same stock snapshot) {% endif %} in draft-only mode — nothing is ever reserved.

What the numbers mean. On this field backlog every open request contains at least one shortage product, so Config B's re-ordering matches A — exactly what the theory predicts: the forecast matters when demand and stock overlap only partially. The controlled scenario tests (ForecastBoostTests, 75-test suite) show B re-ordering and serving an otherwise-starved request in that case. Config C reaches the same fulfilment because the agents must draft through the same engine — the AI adds reasoning, audit trail and narrative, not more food.

5 · What this means (and honest limits)

  • The engine guarantees no invented food and no rule-breaking: every number comes from audited database reads, and every AI draft is a plan a human must approve.
  • The forecast gives a small but real accuracy gain over a naive baseline, and it is exactly what Config B needs to prioritise by predicted shortage.
  • When the LLM is unavailable the system silently degrades — a food bank never stops operating because an API did.
  • Limitations: evaluation replayed policies on synthetic (though realistic) data in draft mode; real-route logistics and per-item pickup confirmation are future work.
